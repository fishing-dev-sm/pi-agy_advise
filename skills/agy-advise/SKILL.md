# agy-advise（Pi 扩展版）

> 本文件只描述 **Pi 扩展** `agy_advise`。MCP 版同名工具（skill `agy-advise-mcp`）行为不同：在临时目录里运行、禁用全部工具、自带项目账本，且不共享会话、不共享权限策略。先确认自己在调哪一个。

让 `agy` 根据目标、约束和观察到的证据独立提出方案。扩展不传 `--mode`，用 CLI 自己的执行模式默认值。文件与命令权限由 `agy` 的配置决定。

## 什么时候问

- 架构、分层或接口取舍会影响后续工作时。
- 已做过一轮实质排查，仍然卡在同一个问题时。
- 删表、改协议、迁移数据等破坏性改动前，需要检查影响范围和恢复方案时。
- 需要独立评审时，把目标和证据交给 `agy`，让它自行找出遗漏的风险或方案。

文件内容、API 签名等可直接查证的事实，明显的拼写错误，以及高频工具循环中的小问题，直接在 Pi 里处理。

## 怎么问

| 参数 | 内容 |
| --- | --- |
| `question` | 用一个开放问题说清目标、已观察到的失败（如有）以及需要判断的事。首次调用要让只看到这条消息的顾问也能理解。 |
| `context` | 可省略，最多 10 行。只给回答所需的事实，例如文件路径和行号、硬约束、有证据支持的排除项。每条一行，省去 Pi 的推理过程和完整聊天记录。 |
| `stance` | 审查立场，默认 `global`（先审前提与主矛盾，再落到下一步与止损）；高风险/不可逆改动前用 `red_team` 做反方挑刺；大方向已锁定只需聚焦细节时用 `tactical`。 |
| `freshSession` | 传 `true` 丢弃活跃会话、发起干净的新会话。切换主题，或担心此前多轮对话产生沉没成本锚定时使用。 |
| `model` / `effort` | 可选模型覆盖（默认读 `AGY_ADVISE_MODEL` 或 CLI 默认）与推理档位（`low`/`medium`/`high`/`xhigh`/`max`）。变更模型或档位会新开会话。 |
| `timeoutMs` | 默认 `240000`（含排队时间）。预计要分析多个文件时，可设为 `300000`。 |
| `skipPermissions` | 省略时按正常权限运行。只有用户明确授权本次绕过权限，并且已告知它可能运行命令或改文件，才传 `true`。如果知道被拦的命令，向用户说明具体命令。 |

**开放问题**「同一 SKU 并发更新时偶发丢失写入。目标是保持现有 API 并保证两次更新都生效。状态在哪一层失去一致性？怎么修复并验证？」

**引导式问法**「你选加锁、重试还是换数据库？我倾向于加锁，你同意吗？」方案本身会影响判断。只有选项已由实际约束限定时，才把这个限制作为事实交代。

## 一次只要一个判断

单次调用只换回一个判断，不要换回一份交付物。要求「任务书 + 分阶段取证顺序 + 检查清单 + 保存哪些命令和 hash + 完成标准 + 下一轮出口」的一次调用，思考和输出会一起超出单轮预算，结果是超时或中途汇报，一项都拿不到。

需要这些内容时切成三次：

1. 「缺上游调用、guest 条件不满足、caller 是 stub，这三种假设哪个与现有证据一致？只回答判断和理由。」
2. 「若假设 1 成立，取证顺序应该是什么？只给顺序，不要写命令清单。」
3. 「把第 2 步展开成可执行清单，每条注明命令、要保存的原始摘录和判定标准。」

每一次都附上一步的结论作为事实。agy 的会话会记住前文，但它看不到 Pi 的对话，所以关键结论要自己带过去。

## 调用方的纪律不要写进 question

在 `question` 里写「不读取文件、不运行命令、不用工具」，不会生效，还会制造两层冲突：

- 那句话是**调用方模型自己的**操作纪律（不贸然派 worker、不 build、不跑 live、不改仓库），不是在约束 `agy`。写进去等于把 Pi 的行为边界伪装成 agy 的任务定义。
- `agy` 在工具结果之后会自行判断回合可以结束，把「我接下来打算……」当成对提问的完整回答。这是回合边界，不是报错，也不是它的能力问题。

两类约束必须分开：

| 约束谁 | 怎么写 | 为什么 |
| --- | --- | --- |
| `agy`：只做只读取证、不改仓库 | 写进 `question`：「只做只读取证，不要改仓库里的任何文件」 | 这是对 agy 行为的要求，但它只是软约束；硬约束靠 `deny` 里的 `write_file(*)` |
| Pi 自己：不派 worker、不 build、不跑 live、不改 live | **不写进 `question`**，由 Pi 自己在本地执行 | 写进去会让 `agy` 误判任务边界，把「只做静态检查」当成全部任务而提前收尾 |

同理，不要把「先不要贸然动手」这类对 Pi 的自我提醒发给 agy。agy 不知道 Pi 的下一步，看到这种话只会理解成「不要给出可执行结论」。

## 工具：放开只读，收紧范围

一句话规则：**会读取内容的能力尽量放开，会改变状态的能力收紧，作用范围锁在项目内。**

禁止工具并不能换来安全，只会把权限问题变成一次空响应，同时让 agy 只能凭猜推理。区分两件事：

| 想防的 | 错误做法 | 正确做法 |
| --- | --- | --- |
| 乱改文件 | 在 `question` 里禁止工具 | `write_file(*)` 进 `deny` |
| 跑危险命令 | 只留 `find`/`ls`/`rg` 白名单 | `toolPermission: "always-proceed"` + `deny` 黑名单 |
| 读到项目外 | 关掉工具 | `allowNonWorkspaceAccess: false`（默认） |

### 不要用 plan 模式

plan 模式（`--mode plan`）在 headless 下是负收益：它要 agy 先写 `implementation_plan.md`，然后等一个 `artifactReviewPolicy` 的复核，而 headless 现场没有人能批。回合就停在「please review and let me approve」。状态是 `SUCCESS`、`response` 非空，扩展不会报错，Pi 只拿到一段过程性文字，这正是「只返回检查进度」的成因。

另有两个附带代价：plan 模式靠展开 `/plan` 斜杠命令实现，和 `--disable-slash-commands` 直接冲突；每轮还多写一份计划文件、多花 thinking。

所以：**不传 `--mode`**。CLI 用它的 headless 默认值（v1.5.7+ 为 `auto`，不可用则 `default`）。本机实测 `auto` 对本账号不可用，会回落到 `default`：

```
warning: --mode auto is not available for this account; continuing in the default mode.
```

实测同一会话不传 `--mode`：`uname -srm` 一条命令 25.7 秒返回 `Linux 7.3.5-arch1-1 x86_64`，brain 目录里没有生成 `implementation_plan.md`，`total_tokens` 11019。

如果确实看到 agy 停下来请示，回一句明确的「Approved, proceed now」就能解除——它把这句话当成批准，同一会话里会直接继续。

### 不维护白名单：用预设 + 黑名单

逐条 `allow` 是错的方向：新增任务就要重新扫一遍命令，漏一条就变成一次空响应。把一个总开关打开、把危险操作关掉，维护量接近零：

```json
{
  "toolPermission": "always-proceed",
  "permissions": {
    "deny": [
      "command(rm)", "command(sudo)", "command(dd)", "command(chmod)",
      "command(chown)", "command(mkfs)", "command(shutdown)"
    ]
  }
}
```

官方文档对 `always-proceed` 的定义是：终端命令、网页请求、MCP 工具都无需询问，**除了命中 ask 或 deny 规则的**。也就是说 deny 在 every mode 下仍然生效，黑名单是最后一道闸。

两个代价要清楚：

- 这是全局设置，**你手工用 agy 时它也不再询问写文件或跑命令**。
- 它不限制范围。`objdump /any/path` 一样放行，靠的是工作区之外默认不可访问（`allowNonWorkspaceAccess: false`）。

要保留逐条审批就把 `toolPermission` 换成 `request-review`；但在 headless 下那等于退回到「一条命令没列进 allow 就整轮空」。`proceed-in-sandbox` 是中间选项，只在 Sandbox Mode 真正生效时有用；Linux 上若内核对 unprivileged user namespace 限制，它会退化成 `request-review`。

### 确实不需要它读代码时

写成「不需要读代码，基于下面给出的事实回答」。这是降低它去读的**动机**，不是保证它不读，也不是命令。真的必须零工具时，就不要用 agy，改用 Pi 自己的模型。

## 调用故障：三种症状

先看错误文本属于哪一种，三种机制的处置完全不同。

| 症状 | 机制 | 处置 |
| --- | --- | --- |
| 返回的是过程性文字（「我先查看…」「还需检查…」），非空、状态成功 | `agy` 在工具结果后自行结束回合，尚未下判断 | 不要回「继续」。补上它缺的判定条件，或改成「基于以上直接给结论」；连续两次仍如此就拆小问题 |
| 空响应，错误里附 stderr | 某条命令需要批准，headless 无法弹窗，被 soft-deny，**整轮取消**但进程 exit 0 | 确认 `toolPermission` 不是 `request-review`；若是，改成 `always-proceed`。不要因此禁止 agy 用工具 |
| `agy planner timed out after Nms` | 工具反复重试，或思考加输出超出单轮预算 | 拆交付物（见上一节），或把 `timeoutMs` 提到 `300000`；重试时问题必须重新自包含 |

**任何失败都会重置会话。** 空响应、超时、进程退出之后，下一次调用是冷启动，不会带上刚才的上下文。所以「失败后再追问」在机制上不存在，重试那条 `question` 必须自己和一次首问一样完整。只有成功的一轮之后才有热追问。

**斜杠命令**如 `/model` 和 `/usage` 不能作为 stream-json 会话的问题发送。需要时在 `agy` 的交互界面中操作。

## 排障顺序

1. 判断症状属于上表哪一种，先不要重复调用。
2. 空响应或超时：查 stderr 或上一次工具序列，确认是不是权限问题。
3. 权限问题：先看 `toolPermission`，headless 下应设为 `always-proceed`；再重试一次，仍失败就报告用户，不要连续重试。
4. 连续两次失败：停止调用 `agy_advise`，把症状、stderr 原文和已试过的处置告诉用户，由用户决定是否继续。

## 冷启动和热追问

- **冷启动**时提供自包含问题。首次调用、切换工作目录、传 `freshSession: true`、切换 `model`/`effort`、本轮失败或超时、进程退出、空闲满 10 分钟或在 Pi 里运行 `/reload` 后，下次调用会建立新会话。
- **热追问**时可以在同一工作目录的活跃 `agy` 会话里只发新增事实和问题。Pi 的对话记录始终独立。只切换 `skipPermissions`（且未改 `model`/`effort`）会重启进程并保留活跃会话 ID。
- 简单问答曾耗时约 20–40 秒，多文件分析约 100 秒。README 中一轮追问的缓存读取约占总 token 的 91%，实际耗时和缓存比例随问题而变。

## 拿到建议后

在本地检查建议依赖的文件、日志或测试，核实它指出的原因以及修复能否满足约束。带着新证据追问，同一问题最多追问 3 次。两次追问后仍有核心分歧或建议依然泛泛时，停止调用，告诉用户各自的依据、已验证结果和仍需做的判断。
